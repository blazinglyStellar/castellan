## Development Setup

### Prerequisites

- Go 1.26.1+
- Docker & Docker Compose
- PostgreSQL 16 (or via Docker)
- Redis 7 (or via Docker)
- [golangci-lint](https://golangci-lint.run/) v2.12+ (local v1.x will not read the config)
- [goose](https://pressly.github.io/goose/) for database migrations
- [sqlc](https://sqlc.dev/) for query code generation

### Quick Start

```sh
# Start infrastructure
docker compose -f deployments/docker-compose.yml up -d postgres redis

# Copy and configure environment
cp .env.example .env
# Edit .env with your database URL, Redis URL, and Stellar testnet keys

# Run migrations
DATABASE_URL="postgres://castellan:castellan@localhost:5432/castellan?sslmode=disable" \
  goose -s -dir migrations postgres "$DATABASE_URL" up

# Build and run
go build -o ./bin/castellan ./cmd/api/
```

### Environment Variables

| Variable            | Default                                                    | Description                    |
|---------------------|------------------------------------------------------------|--------------------------------|
| `DATABASE_URL`      | `postgres://postgres:postgres@localhost:5432/castellan`     | PostgreSQL connection string   |
| `REDIS_URL`         | `redis://localhost:6379`                                   | Redis connection string        |
| `PORT`              | `8080`                                                     | HTTP server port               |
| `STELLAR_HORIZON`   | `https://horizon-testnet.stellar.org`                      | Stellar network endpoint       |
| `WALLET_SECRET_KEY` | —                                                          | Stellar secret key for deposits |

Environment is loaded automatically via `github.com/joho/godotenv/autoload` — a `.env` file in the project root is picked up on startup.

## Project Workflow

### Branch Strategy

- `deploy` is the integration branch. Create feature branches from `deploy` and open pull requests targeting `deploy`.
- `main` is reserved for release-ready commits. It is write-protected — no one pushes directly to `main`.
- Branch naming is flexible, but descriptive names are preferred: `feat/rate-limiting`, `fix/settlement-race`, `chore/update-deps`.

### Commit Messages

We follow conventional commits loosely:

```
feat: add rate limiting to proxy endpoint
fix: correct balance deduction overflow
chore: bump pgx to v5.9.2
docs: update migration instructions
```

There are no strict commit linting rules, but clear messages make the release changelog (generated by goreleaser) more useful.

## Coding Standards

### Go Code

- Follow standard Go idioms: `gofmt` formatting with `gofumpt` extra rules.
- Run `golangci-lint run ./...` before every commit.
- All errors must be handled. Silent discards with `_` are acceptable only when the Go standard library or a well-known API guarantees success (e.g., `json.Marshal` on a `map[string]string`).
- Avoid `panic` outside of `main()` initialization. Return errors instead.
- Use `slog` for structured logging (not `log.Printf`). See [sloglint rules](#sloglint) below.
- Context must be propagated through the call chain. Do not use `context.Background()` outside of `main()` and signal handling.
- Write tests alongside new code. See [Testing](#testing).

### Import Groups

Imports must be grouped in exactly three blocks, separated by blank lines:

```go
import (
	// 1. Standard library
	"context"
	"fmt"
	"net/http"

	// 2. Internal / project packages (module prefix: castellan)
	"castellan/internal/server"

	// 3. Third-party dependencies
	"github.com/jackc/pgx/v5/pgxpool"
	"github.com/julienschmidt/httprouter"
)
```

**This is enforced by gofumpt.** The CI will reject any other grouping. Do not use `goimports` — it conflicts with gofumpt.

### Logging

- Use `context`-scoped loggers: `slog.ErrorContext(ctx, "message", ...)`, not global `slog.Error(...)`.
- All attributes must use `slog.Any("key", val)` or typed variants (`slog.String`, `slog.Int`, etc.). Raw key-value pairs (`"key", val`) are rejected by CI.
- Messages must be lowercase, no trailing punctuation.
- Forbidden attribute keys: `time`, `level`, `msg`, `source`.

```go
// ✅ Correct
slog.InfoContext(r.Context(), "processing request", slog.String("method", r.Method))

// ❌ Wrong — raw key-value pair, CI will reject
slog.InfoContext(r.Context(), "processing request", "method", r.Method)
```

## Linting and Formatting

### CI Config

The repository uses **golangci-lint v2.12** with a custom `.golangci.yml`. Local installations of golangci-lint **must be v2.12+** — v1.x uses a different config format and will silently ignore large parts of the configuration.

If you have v1.x locally, update it:

```sh
go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.12
```

### Running Linters

```sh
# Full lint suite
golangci-lint run ./...

# Lint a specific package
golangci-lint run ./internal/server/...
```

### Common CI Failures and How to Avoid Them

#### 1. gofumpt — "File is not properly formatted"

**Why it happens:** The module name `castellan` is a single-level name (like `fmt`, `http`). When gofumpt runs inside golangci-lint, it cannot auto-detect the module path, so it treats `castellan/internal/server` as a potential stdlib import.

**Fix:** The `.golangci.yml` already sets `module-path: castellan` for gofumpt. Ensure your local formatting matches. Run:

```sh
gofumpt -w <file>
```

Then verify with `golangci-lint run ./...`.

**Common pitfalls:**
- Adding a blank line between every import (must be exactly three groups).
- Using `goimports` locally — it will rewrite imports into a two-group layout that gofumpt rejects.
- Not having `module-path` set when running gofumpt standalone.

#### 2. sloglint — Attribute-style violations

**Why it happens:** The config requires `attr-only: true`, meaning all log attributes must use `slog.Any()`, `slog.String()`, etc.

**Fix:**
```go
// ❌ CI fails
slog.InfoContext(ctx, "message", "key", value)

// ✅ CI passes
slog.InfoContext(ctx, "message", slog.Any("key", value))
```

#### 3. revive — "a blank import should be only in a main or test package"

**Why it happens:** `_ "github.com/joho/godotenv/autoload"` is used in `internal/server/server.go`. This is excluded via a CI rule, but if you add blank imports elsewhere, CI will fail.

**Fix:** Keep blank imports in `main` and test packages only, or add an exclusion rule to `.golangci.yml`.

#### 4. mnd (magic numbers)

**Why it happens:** Bare numeric literals in non-excluded files are flagged.

**Fix:** The following files are excluded: `cmd/api/main.go`, `internal/server/server.go`. If you add magic numbers elsewhere, extract them as named constants.

#### 5. gosec — "Potential hardcoded credentials"

**Why it happens:** The default DSN in `cmd/api/main.go` contains credentials.

**Fix:** This is excluded by a CI rule for `cmd/api/main.go` only. Do not add hardcoded credentials elsewhere.

### Excluded Checks

The following patterns are intentionally excluded from linting:

| Exclusion | Reason |
|---|---|
| `cmd/api/main.go` — gosec hardcoded credentials | Default DSN for local dev |
| `cmd/api/main.go` — mnd magic numbers | Server config uses numeric literals |
| `internal/server/server.go` — mnd magic numbers | Server timeouts use numeric literals |
| `*_test.go` — errcheck, gosec, noctx | Test files have different safety criteria |
| `encoding/json.Marshal` — errcheck | Marshalling a `map[string]string` is always safe |
| Blank import in non-main/test | Acceptable for godotenv autoload |

## Testing

### Running Tests

```sh
# All tests
go test -race -count=1 ./...

# Single package
go test -race -count=1 ./internal/server/

# Single test function
go test -v -run TestHandler ./internal/server/

# Integration tests (requires PostgreSQL)
go test -tags=integration ./integration/...
```

### Test Conventions

- Unit tests live alongside the code they test (`*_test.go` in the same package).
- Integration tests live in `/integration/` and use the build tag `//go:build integration`.
- Use `-race` and `-count=1` to catch data races and disable caching.
- The CI runs unit tests on every push. Integration tests run nightly and on manual dispatch.
- Coverage threshold for CI is 60% (project) and 60% (patch), with 5% tolerance.

## Database Changes

### Migrations

Migrations are managed with [goose](https://pressly.github.io/goose/) in the `migrations/` directory.

```sh
# Create a new migration
goose -s -dir migrations create add_billing_cycle sql

# Apply migrations
DATABASE_URL="postgres://postgres:postgres@localhost:5432/castellan?sslmode=disable" \
  goose -s -dir migrations postgres "$DATABASE_URL" up

# Rollback last migration
DATABASE_URL="postgres://postgres:postgres@localhost:5432/castellan?sslmode=disable" \
  goose -s -dir migrations postgres "$DATABASE_URL" down
```

**Rules:**
- Migrations are **sequential** (numbered `00001_`, `00002_`, etc.). Do not alter existing migration files — create a new one.
- All migrations are pure SQL. No Go migration functions.
- Test your migration with both `up` and `down` before submitting.

### Schema Changes

After creating a migration that adds or modifies schema, you must regenerate the sqlc code:

```sh
cd internal/repository && sqlc generate && cd ../..
```

Commit both the migration and the regenerated Go code together.

## Code Generation

### sqlc

The project uses [sqlc](https://sqlc.dev/) to generate type-safe Go code from SQL queries.

- **Source:** `internal/repository/query/*.sql`
- **Output:** `internal/repository/db/*.go` (checked into version control)

After editing a `.sql` query file:

```sh
cd internal/repository && sqlc generate && cd ../..
```

Then run tests to verify nothing is broken:

```sh
go build ./... && go test ./...
```

**Important:** The generated Go files are committed to the repository. When reviewing a PR, check that both the `.sql` source and the generated output are included.

## Submitting Changes

### Before Opening a Pull Request

1. Run the full lint suite:
   ```sh
   golangci-lint run ./...
   ```
2. Build:
   ```sh
   go build ./...
   ```
3. Run unit tests:
   ```sh
   go test -race -count=1 ./...
   ```
4. Verify your changes compile correctly for the Docker build:
   ```sh
   docker build -t castellan:test .
   ```
5. If you changed queries or schema, regenerate sqlc:
   ```sh
   cd internal/repository && sqlc generate && cd ../..
   ```

### Pull Request Checklist

- [ ] Branch is up to date with `deploy`
- [ ] PR targets the `deploy` branch (not `main`)
- [ ] `golangci-lint run ./...` passes with zero issues
- [ ] `go build ./...` compiles
- [ ] `go test -race -count=1 ./...` passes
- [ ] New code includes tests
- [ ] SQL changes include a migration and regenerated sqlc code
- [ ] Environment variables are documented if new ones are added
- [ ] Commit messages follow conventional commit format

### What CI Will Check

| Check | What it enforces |
|---|---|
| **Lint** | golangci-lint with 40+ linters. See [linting section](#linting-and-formatting) for common failures. |
| **Unit Tests** | All tests pass with race detection. No flaky tests. |
| **Code Coverage** | Project coverage ≥ 60%, patch coverage ≥ 60% (5% tolerance). |
| **Security** | govulncheck (known vulnerabilities) + gosec (code security issues). No HIGH/CRITICAL findings. |
| **Trivy** | Docker image scanned for HIGH/CRITICAL vulnerabilities. No unfixed CVEs above threshold. |
| **Integration Tests** | (Nightly) Full integration suite against PostgreSQL. May require manual trigger for PRs. |

### After Merge

- Merging to `deploy` triggers the lint, security, trivy, and unit test pipelines.
- `deploy` is merged to `main` only when a release is ready. Release is automated: tagging `main` with `v*` (e.g., `v0.2.0`) triggers a goreleaser release that cross-compiles for 6 platforms (linux/amd64, linux/arm64, darwin/amd64, darwin/arm64, windows/amd64, windows/arm64).
